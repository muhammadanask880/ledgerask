# LedgerAsk

Ask your company's sales database a question in plain English and get a real,
data-backed answer — with full visibility into exactly which tool was called
and which SQL query produced the numbers.

> Demo project by **Vento AI**. All data is synthetic, generated by a
> reproducible seed script — no real company information.

## Why this exists

Most "AI + database" demos either (a) give the model raw SQL access and hope
it behaves, or (b) are so locked down they're useless for real questions.
LedgerAsk is built around a narrow, auditable middle ground:

- The AI can **only** call a fixed menu of read-only tools — never raw SQL
  access to the database connection itself.
- Every query the AI generates is validated as a single `SELECT` statement
  before it runs, and the database connection is opened **read-only** at the
  SQLite engine level as a second layer of defense.
- Every row limit, timeout, and SQL statement is enforced in code, not left
  to the model's good behavior.
- Every question and the exact SQL it produced is logged to a file, so the
  "nothing destructive ever happened" claim is checkable, not just asserted.
- The chat UI shows this proof inline, next to every answer.

## Architecture

```
 Browser (sign up / log in / chat)
        │  HTTPS (cookie session)
        ▼
 FastAPI app  (app/main.py)
   ├─ Auth: bcrypt password hashing + JWT session cookie   (app/auth.py)
   ├─ App DB (SQLite): users, chat history                  (app/database.py, app/models.py)
   ├─ Agent loop: OpenAI function-calling                   (app/agent.py)
   │     │
   │     ▼
   ├─ Tool layer: list_tables, describe_table, run_select_query,
   │   revenue_by_month, top_products, sales_by_region       (app/tools.py)
   │     │
   │     ▼
   ├─ Safety gate: SELECT-only, no stacked statements,
   │   forbidden-keyword check, row limit                    (app/safety.py)
   │     │
   │     ▼
   └─ Read-only SQLite connection + hard timeout              (app/business_db.py)
          │
          ▼
    data/ledgerask_business.db   (customers, products, orders,
                                   order_items, regions, sales_reps)
```

The **same tool layer** is also exposed as a real [MCP](https://modelcontextprotocol.io)
server (`mcp_server/server.py`), so it can be used directly from Claude
Desktop or any other MCP client — see "Bonus: Claude Desktop / MCP" below.

The app database (users + chat history) and the business database are two
completely separate SQLite files. The AI's tools never open the app
database, and the app/auth code never opens the business database.

## Setup (Windows / PowerShell)

```powershell
cd C:\Users\HP\OneDrive\Desktop\LEDGERASK
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
# then edit .env and paste your OpenAI API key
python scripts\seed_database.py
uvicorn app.main:app --reload
```

Open http://127.0.0.1:8000 , sign up, and start asking questions.

## Running the tests

```powershell
pytest
```

## Example questions

- "What tables do we have?"
- "What were our top 5 products last quarter?"
- "Which region's revenue dropped last month, and by how much?"
- "Show me monthly revenue for the last 12 months"
- "Delete all orders from last year" → refused; the assistant only has
  read-only access, and `run_select_query` would reject the statement anyway.

## Bonus: Claude Desktop / MCP

The same tool logic is also available as a real MCP server:

```powershell
python mcp_server\server.py
```

To use it from Claude Desktop, copy `claude_desktop_config.example.json`
into Claude Desktop's config file (`%APPDATA%\Claude\claude_desktop_config.json`),
update the paths to match your machine, and restart Claude Desktop.

## Safety notes / known limitations

- This is a portfolio/demo project, not a production security boundary.
  `.env` holds a real API key locally and must never be committed (see
  `.gitignore`).
- Session cookies are `httponly` but not marked `secure`, since the local
  dev server runs over plain HTTP — turn `secure=True` on in `app/auth.py`
  before deploying behind HTTPS.
- Postgres-ready: swapping `business_db.py` for a Postgres connection (with
  an equivalent read-only role) is the natural next step for a real
  deployment; the tool/safety layer above it does not need to change.
